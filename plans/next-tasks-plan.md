### 1.4 비밀번호가 원문으로 통과하는 경우: **있음**

실험: 실제 판단 모델(Laya v3)과 NER 서버로 `Inspector`를 직접 돌렸다(`jev_backend: laya`, NER 기본 켬). 문장 16개를 넣었다. 저장소는 바꾸지 않았다.

- 정규식이 잡는 형태
  - `password: x`, `비밀번호: x`, JSON `"password": "x"`, `ghp_…` 토큰
  - 규칙: 키 이름이 password·secret·token·비밀번호·비번·암호 등으로 끝나고 뒤에 `:`·`=`가 와야 한다(`gate/detectors.py` 27~41줄).
- 정규식이 놓치는 형태
  - 문장 속 비밀번호: "비밀번호는 qwer1234! 입니다", "비번 7741 이야"
  - 짧은 키: `pw:`, `pwd`, `PIN:`, `DB_PASS=`
  - 기타: `admin / P@ssw0rd`, `mysql -pS3cret`, `password 값`(구분자 없음), YAML 블록, "공유기 암호 → 1q2w3e4r", OTP 백업 코드
- 게이트 전체 결과(기본 설정, NER 켬): 대부분은 NER이 우연히 `[연락처]`·`[식별번호]`로 가리거나 판단 모델이 막았다. **그래도 셋이 원문으로 나갔다.**
  - `DB_PASS=Sup3rS3cret`: 같은 파일의 다른 줄만 가려지고 판단 모델이 가린 결과를 safe 0.92로 봐서, 이 줄이 그대로 나갔다.
  - `machine api.example.com login bot password Sup3rS3cret`: NER이 일부만 가렸고 판단 모델이 safe 0.60으로 봐서 그대로 나갔다.
  - `2단계 인증 백업 코드: 8312-4471, 9902-1187`: 아무것도 찾지 못했고 판단 모델이 safe로 봐서 허용됐다.
- NER을 끄면 OTP 백업 코드만 나가고 나머지는 판단 모델이 막거나(deny) 사람에게 물었다.
  - 즉 **NER이 일부를 가리면 판단 모델이 "가린 뒤 안전"으로 보는 쪽으로 기울어**, 정규식이 놓친 비밀번호가 함께 나갈 수 있다(② 흐름의 구멍).
- NER이 비밀번호를 잡는 것은 학습 의도와 다르다. "기타(메신저·SNS 아이디)"·"식별번호"로 잡혔다. 믿을 수 없는 우연이다.

### 1.5 UTF-16·EUC-KR: **원문 통과 확인**

같은 방법으로 세 번 돌렸고 세 번 모두 같았다.

| 파일 | 결과 |
|---|---|
| UTF-16(BOM) `password: …` + `API_TOKEN=sk-live-…` | **허용 · 원문 그대로 나감** |
| UTF-16BE(BOM 없음) `password: …` | **허용 · 원문 그대로 나감** |
| UTF-16(BOM) 카드번호·CVC | **허용 · 원문 그대로 나감** |
| UTF-16(BOM) 상담 기록(이름·휴대폰·주소·주민번호) | 사람 승인(판단 모델 safe 0.87, 확실하지 않음). **승인하면 아무것도 가리지 않고 나감** |
| EUC-KR 상담 기록 + `비밀번호:` | 휴대폰만 가림. **이름·지역은 그대로 나감**(NER이 못 읽음) |
| (비교) UTF-8 같은 상담 기록 | 휴대폰·주민번호·이름·장소 모두 가림 |

- 원인: 게이트는 내용을 UTF-8로 보고(`decode("utf-8", "surrogateescape")`) 정규식·NER·판단 모델에 넘긴다.
  - UTF-16은 글자 사이에 0 바이트가 끼어 정규식이 하나도 맞지 않는다. NER·판단 모델도 깨진 글자를 본다.
  - 판단 모델이 깨진 글을 "안전"으로 보면 원문이 그대로 나간다.
- README "알려진 한계"에 이미 "EUC-KR·UTF-16 파일 … 놓칩니다"라고 적혀 있다. 실제로는 놓치는 정도가 아니라 **허용되어 원문이 나간다.**
